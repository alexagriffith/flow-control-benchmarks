Flow control under pressure

We ran four hardened flow-control scenarios against openai/gpt-oss-20b on one H100-backed vLLM replica. The saturation sweep set the load range, then each scenario ran three complete repeats.

What the benchmark showed

The benchmark showed flow control handling four production traffic patterns under load. Each scenario isolated a different behavior across shared endpoint pressure, priority differentiation, same-priority fairness, and batch inversion prevention.

Test 1
One endpoint, doubled load The endpoint continued routing requests to the same vLLM runtime as aggregate concurrency increased.
Test 2
Priority differentiation Premium traffic stayed steadier while standard traffic absorbed more queue time.
Test 3
Same-priority fairness Premium A spiked, while premium B and C continued in the same priority lane.
Test 4
Priority inversion prevention Batch traffic surged, but higher-priority traffic kept the better scheduling position.

How flow control was exercised

Each request used the same endpoint. The headers told endpoint-picker which priority lane and fairness bucket to use.

  • Model: openai/gpt-oss-20b.
  • Runtime: one H100-backed vLLM replica.
  • Traffic shape: 512 input tokens and 128 output tokens.
  • Measurement: client latency, endpoint-picker queue time, and vLLM running and queued request gauges.

How the benchmark was collected

The benchmark ran from inside the llm-test namespace so the traffic path matched the in-cluster gateway path.

Execution We ran a benchmark script from inside the cluster. Key flags were --pressure-scenarios, --skip-sweep, --scenario-duration 300, --drain-timeout 120, and --repeats 3.
Workload The four scenario tests used the baseline profile: 512 input-token target, 128 output-token cap, and a prompt pool of 384 prompts.
Routing headers Each request carried the inference objective header for priority and the fairness identity header for tenant or workload identity.
Measurements
  • Client samples: status code, throughput, p95 time to first token, and p95 latency.
  • Endpoint-picker metrics: queue time.
  • vLLM metrics: running requests, queued requests, and request-success counters.
Accounting The benchmark used a drain window after each timed scenario so in-flight requests could finish before the next repeat was summarized.
Artifacts The evidence package includes per-run summaries, tenant summaries, metric samples, and a pre-teardown Kubernetes snapshot for auditability.
