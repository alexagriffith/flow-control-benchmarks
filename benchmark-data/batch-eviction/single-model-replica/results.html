Flow control batch eviction benchmark

Can realtime p95 TTFT remain protected while lower-priority batch shares the same GPU?

Reserved capacity and eviction preserve realtime p95 TTFT when batch is already running in vLLM.

When realtime demand needs capacity, eligible batch work is evicted and safely retried through the normal request path.

Realtime p95 TTFT preserved Realtime access remained protected while batch shared the GPU
Batch is safely retried when evicted Evicted work returns through the normal request path
  • Reserved capacity protects realtime before batch fills the engine. The policy keeps capacity available for higher-priority demand.
  • Eviction protects realtime after batch starts running. Eligible lower-priority work yields capacity when realtime demand rises.
  • Retry returns evicted batch work through the normal request path. The Async Processor resubmits the interrupted job.
  • Eviction has a work-recovery cost. An evicted request restarts and may repeat prompt processing.
  • Protection settings trade batch throughput for realtime access. The detailed scenarios show the measured operating points.

How the system is put together

Requests pass through the gateway, the Endpoint Picker, and one vLLM replica on a single H100. Realtime and batch share the same 48-slot concurrency cap. The Endpoint Picker stops running batch streams when higher-priority traffic cannot be admitted.

Eviction's response to blocked priority traffic

Batch filled the GPU. Higher-priority traffic arrived with no free slots. Eviction stopped nine batch streams. Running count fell from 48 toward zero as those jobs wound down. The chart covers one measured clear-out.

When higher-priority requests are turned away

With 25% reserved, three higher-priority requests received HTTP 429 (two in a burst, one with long prompts). With 50% or 75% reserved, none were turned away.

The trade-off Less reserve lets batch use more of the GPU and triggers more evictions. More reserve stops evictions but slows batch throughput. In the one-GPU test, 50% reserve balanced the two.

Latency across headroom settings

50% reserve had the lowest median higher-priority TTFT. No batch streams were stopped in those runs.

Eviction's effect on latency, run to run

Three repeats compared eviction off and on at 25% reserve. All stopped requests retried to completion. Median TTFT was lower with eviction on in two runs and higher in one.

Compute discarded by eviction

When a request is stopped, the work it had already done is thrown away and has to be redone. Longer prompts mean more work thrown away each time.

Operating recommendation

Pattern from the test Reserve capacity for higher-priority traffic. Keep eviction enabled to reclaim slots when batch already runs. Do not treat eviction as a latency knob.
  • Size reserve to the surge. Use expected burst rate and prompt length. 50% reserve worked in the single-GPU test; re-check before quoting a latency target.
  • Plan for retry. The Endpoint Picker returns HTTP 429 on eviction. The batch client must retry with idempotency and backoff.
  • Still open. Multi-GPU pools, full production mix, long endurance runs, and large-prompt admission.

Capability boundary

Claims below passed the evidence gate for the single-replica build.

Supported claims

  • Reserved capacity protected realtime TTFT. Median p95 fell from 561 ms to 341 ms.
  • Eviction stopped running batch streams. 38 vLLM streams terminated when capacity was needed.
  • Retries finished every evicted job. 38 retries, zero duplicate batch results.
  • Priority rules held. Standard traffic reclaimed batch; same-priority batch did not evict peers.
  • Queue survived Async Processor restart. 300 jobs completed once after restart.

Evidence limits

  • Retry owner required. The Endpoint Picker aborts the stream; the Async Processor must resubmit.
  • Eviction is not a TTFT guarantee. Reserved capacity drove the latency result.
  • Request count ignores prompt size. Large prompts raised TTFT before the gate activated.
  • High batch ceiling can reject realtime work. The 75% ceiling failed two pressure shapes.
  • Single replica only. Multi-replica reclamation and cross-node queue recovery were not tested.

Method, configuration, and evidence gate

Model service

  • One NVIDIA H100 GPU
  • GPT-OSS 20B
  • Red Hat AI 3.4 vLLM
  • max-num-seqs: 96
  • max-num-batched-tokens: 8,192

Policy and traffic

  • Endpoint Picker with batch eviction enabled
  • maxConcurrency: 48
  • Priorities: 100, 0, -10
  • Open-loop Poisson, bursts, and session chains
  • Prefix caching disabled and verified

Required evidence

  • Client timing and status
  • Endpoint Picker queue and eviction
  • Envoy request identifier routing
  • vLLM running, waiting, KV cache, and preemption
  • Async retry, final result, deadline, and duplicate checks
Evidence captured August 2026. The final four-way proof contains 12 accepted runs. All 12 data audits passed; 10 met the stricter all-realtime-success performance gate. No fixed service-level objective is claimed.
