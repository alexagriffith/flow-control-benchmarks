In-flight eviction flow control benchmark results

When batch work has filled the GPU, eviction clears room for higher-priority requests by stopping batch jobs already running. It reclaims a full GPU in seconds — but it does not, on its own, make higher-priority requests faster. What keeps them fast is holding capacity aside for them from the start.

  • Eviction responds the instant priority traffic is blocked by batch. When higher-priority requests arrive and batch is holding the capacity, eviction frees it right away.
  • Holding capacity aside is what keeps higher-priority requests fast. The setting that kept 50% aside was the fastest and never needed to evict anything.
  • Eviction's effect on speed was not consistent. The same test, run three times, got faster twice and slower once.
  • Every eviction wastes work. The stopped request has to be redone, and longer prompts waste more.
  • Only the setting that held the least aside turned requests away. Holding 50% or 25% aside turned away none.

How the system is put together

Every request takes the same path: through the gateway, to the router, into the model server. Higher-priority and batch traffic share one GPU. The router is where eviction lives — it is the point that decides, when the GPU is full and higher-priority traffic is waiting, to stop batch work already running.

Eviction's response to blocked priority traffic

Batch work has filled the GPU. Higher-priority traffic arrives and is blocked — there is no room for it. That is the moment eviction responds: it immediately stops batch jobs and hands the capacity to the higher-priority requests. The chart follows one such clear-out from full back to nearly empty.

When higher-priority requests are turned away

Holding only 25% of the GPU aside was not enough for a surge of higher-priority traffic: a few requests were turned away — two in a sudden burst, one with long prompts. Holding 50% or 75% aside turned none away.

The trade-off The less you hold aside for higher-priority traffic, the more often batch fills the GPU and has to be evicted when priority arrives — and eviction throws work away. Hold more aside and evictions stop, but batch gets squeezed into less of the GPU, so batch work finishes slower. The fastest batch and the safest priority pull in opposite directions; the job is to find the point that serves priority without starving batch. In this one-GPU test, holding half aside was that point.

Latency across headroom settings

Holding half the GPU aside for higher-priority traffic was the fastest setting — and it never had to stop any batch work to get there.

Eviction's effect on latency, run to run

We ran the same test three times with eviction off, then on. Every stopped request was retried and finished, but speed went both ways — faster twice, slower once. That is why eviction on its own cannot be counted on to make things faster.

Compute discarded by eviction

When a request is stopped, the work it had already done is thrown away and has to be redone. Longer prompts mean more work thrown away each time.

The operating recommendation

The operating pattern Hold capacity aside for higher-priority traffic — that is what keeps it fast. Keep eviction turned on as a backup that frees the GPU when batch work has filled it. Don't rely on eviction alone to keep things fast.
  • Match how much you hold aside to the size of the surge. Set it against the expected burst of higher-priority traffic and how long the prompts are. Holding 50% aside was the reliable point in this one-GPU test; check it before promising any speed target.
  • Plan for the retry. When a request is stopped, it is not automatically re-sent — the client has to retry it. Batch clients need a retry that is safe to repeat and backs off between attempts.
  • Still to prove. More than one GPU, the real production traffic mix, a long endurance run, and smarter handling of very long prompts.
